  <action>
    Create `sql/phase_38_employee_schedule_read_model_20260322.sql` as an additive, rerunnable migration with the portal schedule read model.

    Required contents:
    1. Query-shaped indexes, following the Supabase Postgres guidance:
       - add a composite index on `schedule_entries(employee_id, date)` with a partial predicate such as `employee_id is not null`
       - add an active-schedule header index on `schedules(outlet_id, start_date, end_date)` where `is_active = true`
       - keep index names explicit and stable so later phases can reference them

    2. A helper pattern for deterministic week boundaries:
       - support an optional `reference_date date default null`
       - compute Monday-start `week_start` and `week_end`
       - if a fallback current date is needed, keep it in one explicit local-date expression instead of scattering `current_date`

    3. A `SECURITY DEFINER` RPC named `get_portal_schedule_week(reference_date date default null)` that:
       - resolves the employee from the authenticated portal session internally using `resolve_portal_employee()` or an equivalent internal lookup
       - does not accept `employee_id`, `outlet_id`, or any other client-controlled identity input
       - joins `schedule_entries` -> `schedules` -> `outlets`
       - filters to the resolved employee plus the computed current-week date range
       - filters to active schedule headers only
       - returns a lightweight row set ordered by `logical_date`, then shift start time

    4. Return fields that are sufficient for both SCHED-01 and SCHED-02 without a second query:
       - `logical_date`
       - `outlet_id`
       - `outlet_name`
       - `shift_name`
       - `start_hour`
       - `start_minute`
       - `end_hour`
       - `end_minute`
       - `is_day_off`
       - `ends_next_day`
       - `notes`

    5. Overnight handling for SCHED-03:
       - keep `logical_date = schedule_entries.date`
       - compute `ends_next_day = true` when the stored shift end is earlier than or equal to the stored start time and the row is not day-off
       - do not duplicate the row onto the next date and do not move the assignment onto the next day

    6. Security and privilege rules:
       - `SET search_path = public`
       - `REVOKE ALL ... FROM PUBLIC`
       - explicit `GRANT EXECUTE ... TO authenticated`
       - do not grant direct table writes to anon or authenticated roles just to power the portal
       - keep the migration additive only; production database changes still require user confirmation before application

    Keep the function output row-based, not JSON-aggregated. The website helper in Plan 02 will derive `todayAssignment` and `upcomingAssignments` from the same dataset.
