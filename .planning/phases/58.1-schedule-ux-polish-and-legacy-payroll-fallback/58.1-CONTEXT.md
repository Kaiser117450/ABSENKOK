# Phase 58.1: Schedule UX polish and legacy payroll fallback - Context

**Gathered:** 2026-03-27
**Status:** Ready for planning
**Source:** User conversation captured during urgent phase insertion and follow-up clarification

<domain>
## Phase Boundary

This phase is a targeted polish and compatibility patch between the shipped Phase 58 payroll matrix baseline and Phase 59 parity work.

It only covers three outcomes:

1. The schedule rules notice in the admin scheduler must stop blocking the workflow by becoming closable or minimizable.
2. The shift-band and required-hours selectors in the schedule assignment flow must remain readable, including on the light chip states that currently render white-on-white text.
3. Payroll recap must keep showing useful legacy results for outlets that still have attendance logs but do not yet have any `schedule_entries`, using employee contract defaults as the fallback source of required hours.

This phase does not redesign scheduling, replace the strict recap engine, or change the Phase 59 portal/PDF parity scope.

</domain>

<decisions>
## Implementation Decisions

### Schedule Rules Notice
- The schedule guidance / policy notice on the jadwal screen is currently too obstructive and must no longer dominate the screen.
- Admins must be able to close it or toggle it into a minimized state.
- The minimized or dismissed state should preserve access to the scheduler controls instead of forcing the notice to stay expanded.

### Shift Picker Readability
- The shift choice UI inside the schedule assignment flow currently has unreadable text because the chip label color blends into the chip background.
- The shift-band chip labels and required-hours chip labels must use a readable dark text color on the light / unselected states.
- This is a visual correctness fix, not a behavior redesign of the shift chooser.

### Legacy Payroll Fallback
- Existing outlets may already have live `attendance_logs` even when `schedule_entries` has not been created or backfilled yet.
- In that legacy state, payroll recap must not go blank just because no schedule entries exist.
- When `schedule_entries` are missing, the recap pipeline must fall back to contract-aware required hours so old data still produces useful recap rows.
- The user expectation is explicit: even without schedule entries, attendance should still be evaluated "apa adanya" against contract defaults so legacy data remains visible.
- For example, when an employee is `PARTTIME`, the fallback must still treat that employee using the part-time required-hours contract instead of dropping the recap row entirely.
- This fallback exists to preserve compatibility with historical/live data before schedule rollout is complete; it must not require a production data migration first.

### Out of Scope
- Creating or backfilling `schedule_entries` for production data is outside this phase.
- Reworking PDF export, portal parity, or broader payroll presentation is deferred to later roadmap phases.

</decisions>

<specifics>
## Specific Ideas

- Preserve the strong Phase 55 / 58 schedule-policy explanation, but make the component operationally lightweight through dismiss/minimize behavior rather than deleting the guidance.
- Treat the reports fallback as compatibility mode for old outlets: recap may be less strict than fully scheduled evaluation, but it must still produce usable rows and spreadsheet output from attendance data already in the database.
- Keep the fallback contract-aware so `FULLTIME` and `PARTTIME` do not collapse into one generic hours assumption.

</specifics>

<deferred>
## Deferred Ideas

- Bulk creation or migration of historical `schedule_entries`
- Any redesign of PDF recap or portal recap surfaces
- Any broader scheduling UX overhaul beyond the obstructive notice and unreadable chip text

</deferred>
