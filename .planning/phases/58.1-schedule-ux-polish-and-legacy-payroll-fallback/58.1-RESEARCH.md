# Phase 58.1: Schedule UX polish and legacy payroll fallback - Research

**Researched:** 2026-03-27

**Confidence:** HIGH

## User Constraints (from CONTEXT.md)

### Locked Decisions
#### Schedule Rules Notice
- The schedule guidance / policy notice on the jadwal screen is currently too obstructive and must no longer dominate the screen.
- Admins must be able to close it or toggle it into a minimized state.
- The minimized or dismissed state should preserve access to the scheduler controls instead of forcing the notice to stay expanded.

#### Shift Picker Readability
- The shift choice UI inside the schedule assignment flow currently has unreadable text because the chip label color blends into the chip background.
- The shift-band chip labels and required-hours chip labels must use a readable dark text color on the light / unselected states.
- This is a visual correctness fix, not a behavior redesign of the shift chooser.

#### Legacy Payroll Fallback
- Existing outlets may already have live `attendance_logs` even when `schedule_entries` has not been created or backfilled yet.
- In that legacy state, payroll recap must not go blank just because no schedule entries exist.
- When `schedule_entries` are missing, the recap pipeline must fall back to contract-aware required hours so old data still produces useful recap rows.
- The user expectation is explicit: even without schedule entries, attendance should still be evaluated "apa adanya" against contract defaults so legacy data remains visible.
- For example, when an employee is `PARTTIME`, the fallback must still treat that employee using the part-time required-hours contract instead of dropping the recap row entirely.
- This fallback exists to preserve compatibility with historical/live data before schedule rollout is complete; it must not require a production data migration first.

#### Out of Scope
- Creating or backfilling `schedule_entries` for production data is outside this phase.
- Reworking PDF export, portal parity, or broader payroll presentation is deferred to later roadmap phases.

### Claude's Discretion
- None explicitly captured in `58.1-CONTEXT.md`.

### Deferred Ideas (OUT OF SCOPE)
- Bulk creation or migration of historical `schedule_entries`
- Any redesign of PDF recap or portal recap surfaces
- Any broader scheduling UX overhaul beyond the obstructive notice and unreadable chip text

## Summary

Phase 58.1 is a narrow compatibility patch between the shipped payroll matrix baseline in Phase 58 and the broader parity work in Phase 59. The repo already contains the correct architectural seams: `ShiftSchedulerScreen` is stateful and owns the obstructive notice plus the unreadable `ChoiceChip` editor; `AdminReportsScreen` already fetches raw attendance rows, active employees, strict recap rows, and then builds one shared `PayrollMatrixDataset` that also drives spreadsheet export.

The safest implementation is additive and local:

1. Keep the scheduler notice, but let the screen collapse or dismiss it so the grid regains priority.
2. Fix the assignment bottom-sheet chips with explicit foreground and background styling instead of relying on theme defaults.
3. Add a compatibility recap fill step that only synthesizes missing employee-date recap rows from legacy attendance data when strict recap rows are absent for those keys.
4. Feed the merged recap rows into the existing matrix builder and existing spreadsheet export service so admin and `.xlsx` output stay aligned.

The important constraint is honesty: the fallback can evaluate required hours, overtime, short work, excess break, and incomplete clock-out states from raw attendance plus employee contract, but it must not invent schedule-only concepts such as lateness or absence when no schedule exists.

**Primary recommendation:** plan Phase 58.1 as one scheduler UX pass plus one gap-filling legacy recap pass inside the existing admin reports pipeline. Do not wait for `schedule_entries` backfill, and do not fork the payroll matrix/export path.

### Pattern 1: Keep scheduler notice state local to `ShiftSchedulerScreen`
**What:** The scheduler screen already renders the notice inline and already owns date navigation and editor state. Add a small bool or two for `expanded` / `dismissed` and pass callbacks into `SchedulePolicySummaryCard`.

**When to use:** The notice should remain available on the screen, but it must no longer consume permanent vertical space.

**Example:**
```dart
// Source: repo pattern from shift_scheduler_screen.dart + local stateful screen ownership
bool _showPolicyNotice = true;
bool _policyNoticeExpanded = true;

if (_showPolicyNotice) {
  SchedulePolicySummaryCard(
    isExpanded: _policyNoticeExpanded,
    onToggleExpanded: () {
      setState(() => _policyNoticeExpanded = !_policyNoticeExpanded);
    },
    onDismiss: () {
      setState(() => _showPolicyNotice = false);
    },
  );
}
```

**Recommendation:** Keep this state in-memory for Phase 58.1. Do not introduce persistence unless the user asks for cross-session behavior later.

### Pattern 2: Style the assignment `ChoiceChip`s explicitly
**What:** The unreadable chips are the bottom-sheet `ChoiceChip`s inside `_showAssignedEntryEditor(...)`, not the schedule grid cells.

**When to use:** Both the shift-band chip group and the required-hours chip group need fixed contrast on unselected, selected, and disabled states.

**Example:**

### Pattern 3: Gap-fill missing recap keys, do not replace strict recap rows
**What:** `AdminReportsScreen._loadDailySummaryData()` already has three inputs the fallback needs: raw attendance rows, active roster rows, and strict recap rows. That is the correct orchestration seam.

**When to use:** After strict rows are fetched and before `buildPayrollMatrix(...)` is called.

**Recommended merge rule:**
- Build a `strictByEmployeeDate` lookup from strict recap rows.
- Derive compatibility rows only from raw attendance groups that have attendance data but no strict recap row for that same `(employeeId, logicalDate)`.
- Merge with `putIfAbsent`, then send the merged rows to `buildPayrollMatrix(...)`.

**Example:**
```dart
// Source: existing buildPayrollMatrix contract + admin_reports_screen load flow
final strictByKey = <String, AttendancePolicyRecapDay>{
  for (final row in strictRows) _recapKey(row.employeeId, row.logicalDate): row,
};

for (final fallback in legacyFallbackRows) {
  strictByKey.putIfAbsent(
    _recapKey(fallback.employeeId, fallback.logicalDate),
    () => fallback,
  );
}

final dataset = buildPayrollMatrix(
  startDate: _startDate,
  endDate: _endDate,
  employees: employees,
  recapRows: strictByKey.values,
);
```

### Pattern 4: Compatibility rows must be honest unscheduled rows
**What:** The fallback should synthesize `AttendancePolicyRecapDay` rows, not a parallel DTO, but it must only compute metrics that are truthful without a schedule.

**When to use:** Legacy outlets with attendance logs and no schedule-derived row for that employee-day.

**Recommended field contract for fallback rows:**
- `shiftBand: null`
- `requiredWorkMinutes: SchedulePolicyService.defaultRequiredWorkMinutes(contract)`
- `lateCutoffLocal: null`
- `breakFirstDeadlineLocal: null`
- `attendanceStatus: sakit / izin / hadirTanpaJadwal`
- `primaryStatus` can be:
  - `sakit`
  - `izin`
  - `hadirTanpaJadwal`
  - `shortWork`
  - `excessBreak`
  - `overtime`
  - `belumAbsenPulang`
  - `activeIncomplete`
- `detailSignals` can include:
  - `hadir_tanpa_jadwal`
  - `short_work`
  - `excess_break`
  - `overtime`
  - `belum_absen_pulang`
  - `active_incomplete`
- Do **not** synthesize:
  - `late`
  - `break_first_confirmed`
  - `absence`

**Why:** `required hours` are contract-based and valid without schedules. `lateness` and `absence` are schedule-derived and would be fabricated.

### Pattern 5: Keep one matrix/export contract
**What:** The fallback exists only to improve recap input completeness. It must not fork output rendering or export.

**When to use:** Always. UI and spreadsheet should both consume the same `PayrollMatrixDataset`.

**Anti-pattern to avoid:** showing compatibility rows in the matrix but leaving spreadsheet export strict-only.

## Common Pitfalls

### Pitfall 1: Treating blank legacy matrices as “no data”
**What goes wrong:** the screen shows a fully rendered payroll table full of `-` placeholders or the “Rekap Policy Belum Tersedia” empty state even though raw attendance exists.
**Why it happens:** `buildPayrollMatrix(...)` creates placeholder cells for active employees when recap rows are empty, and `PayrollRecapTab` only knows about strict recap emptiness today.
**How to avoid:** build fallback rows before `buildPayrollMatrix(...)` and treat `policyError` as non-fatal when compatibility rows were produced.
**Warning signs:** `_dailyRows` is non-empty, `_policyRecapRows` is empty, and the rendered dataset still shows only `-`.

### Pitfall 2: Overriding valid strict rows with compatibility rows
**What goes wrong:** scheduled days lose richer Phase 57 semantics such as `late`, `absence`, `break_first_confirmed`, or manager exemption.
**Why it happens:** a coarse fallback pass rebuilds all days instead of filling only missing keys.
**How to avoid:** merge with `putIfAbsent` on `(employeeId, logicalDate)`.
**Warning signs:** `lateCount` or `absenceCount` unexpectedly drops after fallback is enabled.

### Pitfall 3: Inventing lateness or absence without a schedule
**What goes wrong:** legacy outlets get red lateness/absence penalties that are not backed by a band or schedule assignment.
**Why it happens:** the fallback reuses strict penalty labels without the schedule data those labels depend on.
**How to avoid:** fallback only computes contract-default work and break metrics plus incomplete-day states.
**Warning signs:** fallback rows have non-null `lateCutoffLocal` or `attendanceStatus == tidak_hadir` despite missing schedules.

### Pitfall 4: Reusing `DailySummary` as the final payroll contract
**What goes wrong:** compatibility rows lose Phase 57/58 fields such as `detailSignals`, `primarySeverity`, `requiredWorkMinutes`, and matrix/export semantics drift.
**Why it happens:** `DailySummaryStatus` is intentionally narrow and predates the strict recap contract.
**How to avoid:** use `DailySummary` only as an optional aggregation helper, then map into `AttendancePolicyRecapDay`.
**Warning signs:** new code branches directly on `DailySummaryStatus` inside payroll matrix or spreadsheet logic.

### Pitfall 5: Styling only selected chips
**What goes wrong:** selected chips are readable, but unselected or disabled chips still render low-contrast text.
**Why it happens:** the fix uses `selectedColor` alone and leaves label styling to theme defaults.
**How to avoid:** set label, selected, unselected, and disabled visuals intentionally.
**Warning signs:** chip labels disappear again when `selectedBand == ShiftBand.libur` disables required-hours chips.

## Open Questions

1. **Should fallback trigger only on total recap failure, or also on partial missing employee-date keys?**
   - What we know: the current load path has all three inputs needed for key-level gap fill.
   - What's unclear: whether production gaps are all-or-nothing or mixed by employee-date.
   - Recommendation: plan for key-level gap fill. It is safer and preserves any strict rows that already exist.

2. **Should the notice dismissal persist when the admin leaves and re-enters the scheduler?**
   - What we know: the context only requires that the notice stop blocking workflow.
   - What's unclear: whether the user expects persistence across navigation or app restarts.
   - Recommendation: keep Phase 58.1 in-memory only. Persist later only if the user asks for it explicitly.

3. **How should the UI disclose compatibility mode?**
   - What we know: the fallback is intentionally less strict than fully scheduled evaluation because it lacks schedule data.
   - What's unclear: whether the matrix header needs copy to say that contract defaults were used.
   - Recommendation: add one small info note when fallback rows were injected, especially if strict recap fetch also returned an error.
