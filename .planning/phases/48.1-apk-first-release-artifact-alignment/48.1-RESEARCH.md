# Phase 48.1: APK-first release artifact alignment - Research

**Researched:** 2026-03-23
**Domain:** APK-first v7.0 release contract correction across the tracked packaging helper, manifest semantics, smoke evidence, and operator shell compatibility
**Confidence:** HIGH for the current repo/build-script state and measured host behavior; MEDIUM for future optional `.aab` use because no live downstream bundle consumer is currently tracked

## Summary

Phase 48 already did the expensive work: private upload-key signing, staged release directories, symbol retention, and smoke-verification scaffolding. The urgent gap is that tracked code and operator docs still formalize the wrong final artifact. `tool/release_build.ps1 -CheckOnly` currently reports the signed `.aab` as canonical and omits the `.apk` by default, while the milestone, roadmap, requirements, and state now all say the shipped v7.0 product must remain APK-first.

The strongest repo-specific conclusions are:

1. Phase 48.1 should invert the default retention policy in `tool/release_build.ps1`: build and stage a signed release `.apk` as the canonical retained artifact every time, and only add a `.aab` when an operator explicitly requests the bundle path.
2. The existing `apkRetentionState` plus `smoke-only` manifest semantics are leftovers from the old AAB-first design. Once the canonical release is an APK, the manifest should track optional bundle retention instead.
3. The docs currently tell operators to run `powershell -ExecutionPolicy Bypass -File ...`, which resolves to Windows PowerShell 5.1 on this machine. The smoke check-only lane currently fails there because `tool/release_build.ps1` calls `[System.IO.Path]::GetRelativePath`, even though the same command passes under `pwsh`. Phase 48.1 should fix that mismatch in tracked code instead of pushing a PowerShell-7-only assumption into the runbook.
4. The phase should preserve all Phase 48 foundations: `release_env -> release_preflight`, upload-key signing, versioned staging directories, `--split-debug-info`, optional `mapping.txt`, and `smoke-check.txt`. This is a contract correction, not a reimplementation.

## Current State Analysis

### 1. Measured helper output is still AAB-first

Key command evidence from 2026-03-23:

```text
powershell -ExecutionPolicy Bypass -File tool/release_build.ps1 -CheckOnly
  Canonical .aab  : ...\ABSENKOK-v7.0.0+8013.aab
  APK retention   : omitted
  Real build flow : release_env.ps1 -> release_preflight.ps1 -> flutter build appbundle --release ...
```

That directly conflicts with:

- `.planning/ROADMAP.md` -> Phase 48.1 goal and success criteria
- `.planning/REQUIREMENTS.md` -> `REL-02`, `REL-03`
- `.planning/STATE.md` -> current focus is re-centering the final product on optimized signed APK output

### 2. Smoke verification works in `pwsh`, but not in the documented `powershell` host

Measured command evidence from 2026-03-23:

```text
Get-Command powershell -> C:\WINDOWS\System32\WindowsPowerShell\v1.0\powershell.exe
powershell -NoLogo -NoProfile -Command '$PSVersionTable.PSVersion.ToString()' -> 5.1.26100.7920
Get-Command pwsh -> C:\Program Files\PowerShell\7\pwsh.exe
pwsh -ExecutionPolicy Bypass -File tool/release_build.ps1 -CheckOnly -SmokeVerify -> passes
powershell -ExecutionPolicy Bypass -File tool/release_build.ps1 -CheckOnly -SmokeVerify -> MethodNotFound on [System.IO.Path]::GetRelativePath
```

That means the current operator-facing command contract is internally inconsistent. Either the docs switch to `pwsh` everywhere or the helper becomes Windows PowerShell compatible. Because the tracked release docs from phases 47-48 already standardize on `powershell`, compatibility is the smaller and safer correction.

### 3. The stale manifest semantics come from the old artifact policy

Current tracked surfaces still use AAB-first vocabulary:

- parameter: `-IncludeSideLoadApk`
- manifest field: `apkRetentionState`
- special state: `smoke-only`
- operator doc language: signed `.aab` is canonical; `.apk` is exceptional

Those names only make sense when the `.aab` is the default retained artifact. In an APK-first lane:

- the retained APK is normal, not exceptional
- smoke verification can use the canonical retained APK
- the exceptional path becomes optional bundle generation/retention

### 4. Phase 48 already established the foundations that 48.1 must preserve

Tracked code and docs already provide the following and should not be reopened:

- `tool/release_env.ps1` pins Java 21 JBR plus the canonical `C:\flutter\bin\flutter.bat`
- `tool/release_preflight.ps1` fails before package/sign work
- `tool/release_build.ps1` already stages outputs under `build/releases/android/ABSENKOK-v<versionName>+<versionCode>/`
- `tool/release_build.ps1` already retains `symbols/`, copies `mapping.txt` when present, and writes `smoke-check.txt`
- `android/app/build.gradle.kts` already routes `release` through the private upload-key flow from Phase 48-01

The phase boundary is therefore "correct the live artifact contract" rather than "invent a new release system."

### 5. Phase 49 should inherit one corrected contract, not two conflicting ones

Phase 49 is supposed to document and prove one operator flow. If Phase 48.1 only changes part of the helper or only changes the docs, Phase 49 will inherit contradictory guidance:

- roadmap/requirements/state say APK-first
- operator helper/doc still say AAB-first
- smoke verification behaves differently depending on whether the operator uses `powershell.exe` or `pwsh`

Phase 48.1 should leave Phase 49 with one stable command surface, one manifest vocabulary, and one canonical retained artifact.

## Recommended Architecture

### Pattern 1: Make APK the canonical retained artifact and default build output

`tool/release_build.ps1` should:

- always build and stage the signed release `.apk`
- treat that APK as the canonical retained Android artifact
- only build/retain a `.aab` when an operator explicitly requests it

An explicit switch such as `-IncludeAppBundle` is clearer than reusing `-IncludeSideLoadApk`, because the latter bakes the old AAB-first assumption into the helper interface.

### Pattern 2: Replace APK-retention manifest fields with bundle-retention semantics

The manifest should stop describing the APK as exceptional. Recommended shape:

- `canonicalArtifact` -> staged APK path
- `bundleRetentionState` -> `retained` or `omitted`
- no `smoke-only` state, because smoke verification can install the canonical retained APK directly

That keeps the manifest vocabulary aligned with the new operator contract.

### Pattern 3: Keep smoke verification anchored to the canonical APK

Smoke verification should install and launch the same staged APK that Phase 49 will ask operators to distribute. The evidence bundle should remain:

```text
ABSENKOK-v<versionName>+<versionCode>/
  ABSENKOK-v<versionName>+<versionCode>.apk
  symbols/
  mapping.txt
  smoke-check.txt
  release-manifest.json
  optional .aab only when explicitly requested
```

That removes the need for a special smoke-only APK branch and keeps every debugging artifact tied to the same retained release record.

### Pattern 4: Make the documented `powershell` lane truthful

The repo already documents `powershell -ExecutionPolicy Bypass -File ...` commands. The release helper therefore needs to support Windows PowerShell 5.1 for:

- `-CheckOnly`
- `-CheckOnly -SmokeVerify`
- manifest path serialization during real builds

If the helper remains `pwsh`-only, Phase 49 would need to rewrite every release instruction around that runtime requirement. Fixing the compatibility bug in `tool/release_build.ps1` is the narrower change.

### Pattern 5: Preserve history; update only the live operator surfaces

Phase 48 planning files and summaries should remain as historical evidence explaining why Phase 48.1 exists. The live correction belongs in:

- `tool/release_build.ps1`
- `docs/android-release-contract.md`

Do not rewrite archived or completed phase summaries just to hide the drift.
