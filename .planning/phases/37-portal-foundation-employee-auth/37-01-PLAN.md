  <action>
    Create `sql/phase_37_employee_portal_foundation_20260322.sql` as an additive, rerunnable migration with six pieces:

    1. Search normalization support for employee-name lookup:
       - Create an immutable helper such as `normalize_portal_search_text(text)` that lowercases, trims, and collapses repeated spaces
       - Add a stored/generated column or equivalent maintained search field, for example `employees.portal_search_name`
       - Do not overwrite the visible `employees.name`

    2. Indexes for fast login search:
       - Add a prefix-search index on the normalized search field using `text_pattern_ops`
       - Scope the index to active, non-archived employees only
       - Add `CREATE EXTENSION IF NOT EXISTS pg_trgm`
       - Add a trigram GIN index on the same normalized search field for fallback fuzzy matching when the query is at least 3 characters long

    3. A new `employee_portal_accounts` table:
       - `employee_id uuid primary key references employees(id) on delete cascade`
       - `auth_user_id uuid unique not null`
       - `auth_email text unique not null`
       - `enabled_at timestamptz not null default now()`
       - `provisioned_by uuid null`
       - `last_password_reset_at timestamptz null`
       - `created_at timestamptz not null default now()`
       - `updated_at timestamptz not null default now()`

    4. A `SECURITY DEFINER` RPC named `search_portal_employees(search_text text, limit_count integer default 8)`:
       - normalize the incoming search text once
       - return an empty result for very short queries rather than scanning broadly
       - search only active, non-archived employees that already have portal access provisioned
       - return a lightweight card payload with at least `employee_id`, `employee_name`, `home_outlet_id`, `home_outlet_name`, `position`, `photo_url`, and `active_badge_id`
       - prefer left-anchored prefix matches first
       - allow trigram fallback only for queries with enough characters to justify it
       - cap results at a small number so the login UI never pulls a large directory

    5. RLS and helper behavior:
       - admin may select portal accounts
       - employee portal users may only read their own mapping if needed
       - keep all writes privileged through SECURITY DEFINER or Edge Function paths; do not open direct anon writes
       - keep search RPC executable only through approved roles used by the website server path

    6. A `SECURITY DEFINER` resolver RPC named `resolve_portal_employee()`:
       - derive the authenticated auth user from `auth.uid()`
       - join `employee_portal_accounts` to `employees`
       - only return an active, non-archived employee row
       - raise or return a blocked/null result when zero rows or more than one row match
       - include the minimum phase-37 context needed by the portal shell: `employee_id`, `employee_name`, `position`, `home_outlet_id`, `home_outlet_name`, `photo_url`, `active_badge_id`

    Follow the project's established SQL conventions:
       - `CREATE TABLE IF NOT EXISTS`
       - `CREATE OR REPLACE FUNCTION`
       - `SECURITY DEFINER`
       - `SET search_path = public`
       - `REVOKE ALL ... FROM PUBLIC` and explicit `GRANT EXECUTE ... TO authenticated`
       - additive only; do not rewrite existing employee data destructively
  </action>

    3. Accept `{ employee_id, password }` from the caller. Do not accept raw names, outlet ids, or browser-selected labels as source-of-truth input.

    7. Insert the mapping row into `employee_portal_accounts`.
    8. Return a small success payload with the employee id, employee name, auth user id, and created timestamp.

    Error-handling rules:
    - Return user-facing JSON errors for duplicate provisioning, invalid employee state, or auth creation collisions
    - Keep service-role usage entirely inside the Edge Function
    - Centralize hidden-email creation in one helper so later plans can reuse the same rule
