# Milestone v6.1: Employee Portal

**Status:** ✅ SHIPPED 2026-03-23
**Phases:** 37-39
**Total Plans:** 8

## Overview

Launch the first employee-facing ABSENKOK web portal so staff can securely see their own schedules without touching kiosk or admin-only surfaces. The milestone established portal provisioning, password-based employee login, employee-scoped schedule retrieval, mobile-first portal UX, and a later hardening pass on the website read path.

## Phases

### Phase 37: Portal Foundation & Employee Auth

**Goal:** Extend the Astro website into a protected employee portal with provisioning, fast name-search sign-in, and stable employee identity resolution.
**Depends on:** None
**Plans:** 4 plans

Plans:

- [x] 37-01: Portal account contract, search index, and provisioning function
- [x] 37-02: Admin employee portal provisioning flow
- [x] 37-03: Astro portal auth and search infrastructure
- [x] 37-04: Protected portal shell and employee context

**Details:**
- Requirements: `AUTH-01`, `AUTH-02`, `AUTH-03`, `LINK-01`
- Added a deterministic employee portal auth contract and indexed name search in Supabase
- Built an admin-side provisioning flow for initial employee portal access
- Added SSR-safe portal auth, search, sign-in/sign-out routes, and middleware in the Astro website
- Established server-side employee resolution before any schedule data is rendered

### Phase 38: Employee Schedule Read Model

**Goal:** Expose a safe, employee-scoped schedule query path that matches existing scheduling rules.
**Depends on:** Phase 37
**Plans:** 2 plans

Plans:

- [x] 38-01: Employee-scoped schedule RPC and indexes
- [x] 38-02: Website helper and basic schedule visibility

**Details:**
- Requirements: `SCHED-01`, `SCHED-02`, `SCHED-03`
- Added the first employee-scoped schedule read model for portal use
- Surfaced today's shift and current-week schedule inside the protected portal
- Preserved logical-day and overnight handling so portal output matched existing scheduling rules
- Later website hardening replaced the original current-week RPC with `get_portal_schedule_overview` for the shipped portal path

### Phase 39: Employee Portal Schedule UX

**Goal:** Deliver the mobile-first employee portal pages that surface schedule data safely and clearly.
**Depends on:** Phase 38
**Plans:** 2 plans

Plans:

- [x] 39-01: Portal home state model and mobile schedule components
- [x] 39-02: Portal-only logout plus portal shell/page wiring

**Details:**

- Added discriminated portal home states for loading, empty, not-linked, error, and ready modes

- Final shipped website revision also added next-week schedule visibility, red status cards for `libur` and `sakit`, and icon-only `izin` / `sakit` badges

## Milestone Summary

**Decimal Phases:**

- None

**Key Decisions:**

- Hidden portal auth email uses `employee+<uuid>@portal.absenkok.internal`
- Portal search normalization stays in Postgres via generated column + trigram fallback gating
- Astro portal middleware validates server-side auth with `getUser()`
- Portal schedule UI derives current and upcoming surfaces from one schedule dataset
- Final website hardening moved the shipped read path to authenticated RPCs and tightened RPC ACLs

**Issues Resolved:**

- Employees now have a dedicated self-service portal separate from kiosk and admin surfaces
- Portal auth resolves one employee identity before any schedule read occurs
- Employees can see today's shift, this week, and next week from a phone-friendly portal layout
- Portal logout no longer risks ending kiosk or admin sessions

**Issues Deferred:**

- Phase 37 has no approved verification artifact
- Phase 38 and 39 validation artifacts remained draft at closeout
- Planning summaries were not backfilled after the shipped website hardening pass
- Attendance recap, requests workflow, and notifications remain future portal scope

**Technical Debt Incurred:**

- Milestone archived with accepted audit status `gaps_found`
- Planning still references `employee_portal_accounts` / `get_portal_schedule_week` while the shipped website path now uses `resolve_portal_employee` and `get_portal_schedule_overview`
- Verification discipline for cross-repo portal work needs to be re-established before the next milestone
