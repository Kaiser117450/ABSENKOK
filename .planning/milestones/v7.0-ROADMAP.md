## Milestone Summary

**Decimal Phases:**

- 48.1: APK-first release artifact alignment

**Key Decisions:**

- Java 21 via Android Studio JBR is the supported Gradle runtime until a dedicated compatibility spike proves a different baseline.
- Release builds use a private upload-key configuration instead of the debug keystore, while the signing files remain machine-local and untracked.
- The signed optimized `.apk` is the canonical retained Android release artifact; `.aab` output stays optional behind `-IncludeAppBundle`.
- `tool/release_build.ps1` records obfuscation, split-debug-info, mapping, smoke verification, and git metadata truthfully in `release-manifest.json`.
- The final published v7.0 GitHub release asset is the obfuscated smoke-verified `ABSENKOK-v7.0.0+8013.apk`.

**Issues Resolved:**

- Canonical Windows release packaging no longer depends on the broken spaced Flutter SDK path.
- Version/build metadata and staged artifact names now align with `7.0.0+8013`.
- Release preflight now fails before signing when analysis, tests, or release-only compilation are red.
- The tracked `release` lane no longer falls back to the debug signing configuration.
- Artifact retention, smoke evidence, and operator documentation now agree on an APK-first release contract.
- GitHub Release `v7.0.0` now has the final obfuscated smoke-verified APK asset published from the staged release directory.

**Issues Deferred:**

- Automated GitHub Release / CI publishing on top of the proven local lane
- Build-speed optimization and incremental caching work
- APK size/runtime tuning beyond the stable signed baseline
- Play Store / bundle-first distribution work
- Employee portal correction, time-off, approval, and notification flows

**Technical Debt Incurred:**

- No dedicated `v7.0-MILESTONE-AUDIT.md` was produced; closeout proceeded anyway after the user accepted the missing audit and all 9 milestone requirements were already complete.
- The real upload keystore and `android/key.properties` remain intentionally machine-local, so operator bootstrap is still required on each release machine.
- Shell `java` can still drift away from the supported JBR path; operators must enter the lane through `tool/release_env.ps1` or `ABSENKOK_JAVA_HOME`.
- GitHub release publication still needs `gh` CLI fallback in this environment because the app automation could not read the local staged artifact path directly.
